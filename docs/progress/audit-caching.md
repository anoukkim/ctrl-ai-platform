# 프롬프트 캐싱 점검 (PART F1, 2026-10-14)

근거 문서: Anthropic 공식 Prompt caching 페이지
<https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching>
(2026-10-14에 읽음). 아래의 "공식" 숫자는 모두 이 페이지에서 왔습니다.

## 1. 카탈로그 모델별 공식 사양

| 모델 | 캐시 최소 길이 | 수명 | 쓰기 요금 | 읽기 요금 |
| ---- | -------------- | ---- | --------- | --------- |
| Haiku 4.5 ($1 in) | **4,096 토큰** | 5분 (쓸 때마다 무료 연장; 1h 옵션) | 1.25× = $1.25 (5m) / 2× = $2 (1h) | 0.1× = **$0.10** |
| Sonnet 5.5 ($2 in) | 512 토큰 | 〃 | $2.50 / $4 | 0.05× = **$0.10** |
| Opus 5.5 ($4 in) | 512 토큰 | 〃 | $5 / $8 | 0.05× = **$0.20** |

공통 규칙:

- 수명은 **요청이 시작된 시점부터** 셉니다. 4분짜리 스트리밍이 끝난 뒤
  이어 보내려면 약 1분 안에 보내야 같은 캐시를 읽습니다.
- 캐시 지점(breakpoint)은 요청당 **최대 4개**. 자동(top-level) 마커도
  그 4자리 중 하나를 씁니다.
- 무엇이 캐시를 깨뜨리나: 도구 목록 변경은 **전부** 무효화. 웹 검색
  켜고 끄기는 시스템 프롬프트가 바뀌는 효과라 tools 캐시만 살아남고
  system/messages는 무효화. thinking 설정 변경은 메시지 블록 무효화.
  모델이 바뀌면 전부 무효화. 이미지 추가/삭제는 메시지 블록.
- usage 필드: `cache_creation_input_tokens`(쓴 양),
  `cache_read_input_tokens`(읽은 양), `input_tokens`(**마지막 캐시 지점
  뒤의** 토큰만). 서버 도구(웹 검색)의 결과는 자동으로 캐시됩니다.

## 2. 우리 코드 대조

| 공식 사실 | 우리 코드 | 판정 |
| --------- | --------- | ---- |
| 지점 최대 4개 | 2개: 시스템 프롬프트 블록의 명시 마커 + top-level 자동 마커 (`claude_provider.request_params`) | ✅ 여유 2개 (chat-plus-files/tools가 쓸 수 있음) |
| 앞부분 1바이트만 달라도 미스 | 시스템 프롬프트는 상수, 히스토리는 저장된 메시지를 `\n\n`로 합치고, 잘라내기는 **계단식**(`_stable_start`)이라 시작점이 반 한도만큼 자랄 때까지 고정. 시간·ID·회원 이름이 프롬프트에 들어가지 않음 | ✅ 새 테스트 `test_two_consecutive_turns_share_a_byte_identical_cached_prefix`가 실제 SDK 요청 본문으로 못 박음 |
| 도구 목록 변경은 전부 무효화 | 도구는 **대화 단위** 토글(chat-plus-tools) — 턴마다 같은 tuple이 그대로 감. 토글하면 그 대화의 캐시가 한 번 깨지는 것이 맞고, 화면의 비용 안내가 그렇게 말함 | ✅ |
| thinking 설정 변경은 무효화 | `CHAT_THINKING`/`CHAT_EFFORT`는 서버 설정으로 고정, 요청마다 같음 | ✅ (운영자가 .env를 바꾸면 한 번 깨지는 것뿐) |
| 쓰기 1.25×/2×, 읽기는 모델별 | `Price.cache_write_usd_per_mtok`(1.25×/2×)와 카탈로그의 `cache_read_usd_per_mtok` | ✅ 요금 산식 테스트 통과 |
| Sonnet 5.5 읽기 $0.10 | 시드가 **$0.20**이었음 — 회원이 캐시 읽기를 정가의 2배로 차감당함 | ❌→✅ **고침**: 시드 $0.10 + 마이그레이션 `f7c3a9e1d5b2` (옛 시드값 0.20을 가진 행만 0.10으로; 관리자가 직접 적은 값은 그대로). 지난 차감 기록은 역사라 그대로 둡니다 |
| Haiku 4.5 최소 4,096 토큰 | 시스템 프롬프트는 약 2,300자 ≈ 실측 500~600 토큰. **짧은 Haiku 대화는 캐시가 아예 안 잡힙니다** — 대화(히스토리 포함)가 4,096 토큰을 넘어야 그때부터 캐시 | ⚠ 그대로 둠(문서화). 고치려면 시스템 프롬프트를 억지로 4천 토큰으로 늘려야 하는데, 배보다 배꼽. Haiku는 입력이 싸서($1/MTok) 손해도 작음 |
| Sonnet/Opus 최소 512 | 시스템 프롬프트 단독으로 512 언저리 — 첫 턴부터 캐시가 잡히거나, 짧아도 두 턴째부터는 확실히 잡힘 | ✅ |
| `input_tokens`는 마지막 지점 뒤만 | 원장이 uncached/write/read를 **각각** 기록하고 각자 요금으로 계산; 지갑 차감 = 세 몫의 합 (기존 prompt-caching 테스트) | ✅ |

mock도 같은 규칙을 흉내 냅니다(모델별 최소 길이, 수명, 모델별 분리) —
키 없이 전 과정을 테스트한 근거입니다.

## 3. 관리자 화면

**Admin › AI Models › 비용 보정 › 캐시 절약**: 모델·일(KST)별로 답장 수,
캐시 적중률, 캐시에서 읽은 토큰, **캐싱이 아낀 원화**(읽은 토큰 ×
(입력 요금 − 읽기 요금) × 그 사용의 환율; 요금은 오늘 카탈로그 기준의
어림이라고 화면에 적음). `GET /api/admin/chat-models/cache-stats`.

## 4. 아침에 실제 키로 확인하는 법 (MORNING §7용)

1. 실제 Claude를 켠 뒤(MORNING §5), Chat에서 **같은 대화**에 짧은
   메시지를 **두 번** 보냅니다. (기본 모델 Sonnet 기준)
2. Admin › Audit… 이 아니라 **Usage 최근 내역**이나 DB가 아니라, 가장
   쉬운 곳: **Admin › AI Models › 비용 보정 › 캐시 절약**에서 오늘
   줄의 "캐시에서 읽음"이 0보다 커졌는지 봅니다. (두 번째 답장의 사용
   기록에 `cache_read_tokens > 0`이 쌓인 것입니다.)
3. **0이면**: ① 두 번째 메시지를 5분 넘게 늦게 보냈거나(캐시 만료),
   ② 모델이 Haiku라 대화가 아직 4,096 토큰이 안 되거나(위 표),
   ③ `.env`의 `CHAT_PROMPT_CACHE`가 꺼져 있는 경우입니다. Sonnet으로
   바로 이어 보내면 반드시 잡혀야 하고, 그래도 0이면 저에게 알려
   주세요.
4. 요금 감: 두 번째 답장의 차감이 첫 번째보다 눈에 띄게 작으면(입력이
   길수록 차이가 큼) 캐싱이 일하고 있는 것입니다.
